## Bctx DeepSeek 验证结果

输入为 R4 已有的 468 个 exact-q 正负回答组。按文档设计，每组需要 2 行、2 个输入模式、2 个 DeepSeek 模型，共 3744 个验证请求。

实际执行：

| 指标 | 数值 |
|---|---:|
| exact-q 候选组 | 468 |
| DeepSeek 验证请求 | 3744 |
| 完整组 | 468 |
| strict validated pass groups | 130 |
| 需要组数 | 360 |
| Anchor 可用组 | 70 |
| Model-Dev 可用组 | 60 |
| selected mean context_gain | 0.2942 |
| selected median context_gain | 0.2500 |
| selected y_only acc | 0.6423 |

Bctx 的质量梯度是存在的：通过组的平均 context_gain 达到 0.2942，中位数 0.25，y-only acc 低于 0.78，说明“加入 q 后更容易判定”的方向成立。但容量不成立：strict 通过组只有 130，远低于 360；来源占比也偏向 PKU，PKU 约 86.15%，BeaverTails 约 13.85%，没有达到 25%-75% 的来源占比要求。

因此 Bctx 当前不是效果问题，而是候选容量问题：R4.1 文档假设 468 个 exact-q 组中可筛出 360 个上下文有效组，实证结果不支持该假设。

这说明 Qwen 在 Helpful-Assistant 与 Role-play 单轮设置下对 Fraud-R1 大多数诱导场景仍倾向安全回应。这个现象本身有论文价值，但它不支持 R4.1 设想的 Panel C 平衡构造。

## 为什么没有进入 G0/大规模 Anchor

R4.1 的运行顺序要求先通过 Bctx 与 Panel C，再进入 G0。当前：

| Gate | 结果 |
|---|---|
| Cache Audit | PASS |
| Bctx | STOP |
| Panel C | STOP |
| G0 | 未运行，上游 Gate 不满足 |
| Model-Dev | 未运行，上游 Gate 不满足 |
| Anchor | 未运行，上游 Gate 不满足 |
| Stability | 未运行，上游 Gate 不满足 |

如果强行进入 G0，需要放宽 Bctx 的正增益要求、取消来源占比限制或取消 Panel C 的中英文 unsafe 平衡。这会违背本轮文档的准入逻辑，也会让后续 q/y/q+y 指标缺乏可信的数据构造依据。因此本轮正确收尾是保留完整缓存和审计，报告 STOP。
